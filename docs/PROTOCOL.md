# Device Ingestion Protocol

This document is the contract between a device (or the simulator) and the platform's ingestion API. It covers device identity, the event schema, the single and batch endpoints, how duplicates and retries behave, and how a device should handle going offline and reconnecting.

**Model in one paragraph:** devices send JSON events over HTTP. Delivery is **at-least-once**: a device keeps each event until the API acknowledges it, and may send it more than once. The platform makes that safe by treating `eventId` as an idempotency key, so a repeated event is recognised and ignored.

This document covers the device endpoints only. The dashboard endpoints (`/v1/devices`, `/v1/incidents`, `/v1/stream` and so on) are separate and are not authenticated with a device key.

---

## 1. Device identity and authentication

Each device has a `deviceId` and an API key.

- **Header:** `x-api-key: <key>` on every ingestion request. Header names are case-insensitive.
- **Key format:** `fleet_` followed by random hex. The server stores only a **SHA-256 hash** of the key (`apiKeyHash`); the plaintext key is shown once, in the registration response.
- **Ownership:** the key must belong to the `deviceId` in the event. Missing or invalid keys get `401`.
- **Caching:** after a successful check, the server may cache the device identity in Redis (keyed by the key hash). The database remains the source of truth.

### Registration: `POST /v1/devices`

```http
POST /v1/devices
Content-Type: application/json

{
  "deviceId": "device-sensor-042",
  "name": "Warehouse Sensor 42",
  "location": "tokyo-dc1"
}
```

Response `201 Created`:

```json
{
  "status": "created",
  "deviceId": "device-sensor-042",
  "name": "Warehouse Sensor 42",
  "location": "tokyo-dc1",
  "apiKey": "fleet_<shown-once>",
  "createdAt": "2026-10-25T12:00:00.000Z"
}
```

Notes:

- Registering an existing `deviceId` returns `200` with the existing record and does **not** issue a new key. A device that loses its key therefore cannot recover it through this endpoint (see [LIMITATIONS.md](LIMITATIONS.md)).
- Registration is open: it needs no credentials. That is acceptable for a local demo and is listed as a limitation for production.

## 2. Event schema

| Field | Type | Required | Description |
| :--- | :--- | :---: | :--- |
| `eventId` | string (UUID) | yes | Generated by the device. The idempotency key. |
| `deviceId` | string | yes | The device that produced the event. |
| `seq` | integer, 0 or greater | yes | Counter that increases with every event from this device. |
| `type` | string | yes | Event type. Conventional values are `reading`, `heartbeat`, `error` and `status`. Rules of type `type_match` fire on this value. |
| `timestamp` | string (ISO-8601) | yes | When the device produced the event, by the device's clock. |
| `payload` | object | yes | Measurements. See below. |
| `replayed` | boolean | no | `true` if the event was buffered while offline and is being resent. Default `false`. |

**Payload.** Threshold rules read a metric and a value. The recommended form is:

```json
{ "metric": "temperature", "value": 74.5 }
```

A flat form such as `{ "temperature": 74.5 }` is also understood by the rules engine. Heartbeats can carry any object, for example `{ "uptime": 350, "status": "ok" }`.

**Validation.** `eventId` must be a UUID, `seq` an integer of at least 0, `timestamp` a valid ISO-8601 datetime, and `payload` a JSON object. A request body size limit also applies.

## 3. Single event: `POST /v1/events`

```http
POST /v1/events
Content-Type: application/json
x-api-key: fleet_<your-key>

{
  "eventId": "a814187e-07a8-486a-b27b-2016335017e4",
  "deviceId": "device-sensor-042",
  "seq": 142,
  "type": "reading",
  "timestamp": "2026-10-25T12:05:30.123Z",
  "payload": { "metric": "temperature", "value": 74.5 }
}
```

### Responses

| Status | Meaning | What the device does |
| :---: | :--- | :--- |
| `202` | `status: "accepted"`. The event is stored and queued for processing. | Delete it from the local buffer. |
| `200` | `status: "duplicate"`. The platform already has this `eventId`. | Delete it from the local buffer. |
| `400` | Validation failed (or malformed JSON). The event is stored in `rejected_events` with the reason. | Do not resend the same content. Fix or discard it. |
| `401` | Missing or invalid key, or the key does not belong to this `deviceId`. | Re-register or fix credentials. Keep the event. |
| `429` | Rate limit or queue backpressure. Body has `code: "rate_limited"` or `"queue_full"`, and a `Retry-After` header. | Wait, then resend. Keep the event. |
| `503` or other `5xx` | The platform could not complete the request. | Keep the event and retry with backoff. |

Example bodies:

```json
{ "status": "accepted", "eventId": "a814187e-...", "receivedAt": "2026-10-25T12:05:30.245Z" }
```

```json
{ "status": "duplicate", "eventId": "a814187e-...", "message": "Duplicate event, already received" }
```

```json
{ "error": "Validation failed", "details": [{ "path": ["seq"], "message": "seq must be a number" }] }
```

## 4. Batch: `POST /v1/events/batch`

Used to send many events at once, typically a buffer after reconnecting.

```http
POST /v1/events/batch
Content-Type: application/json
x-api-key: fleet_<your-key>

{
  "events": [
    {
      "eventId": "b1111111-0000-4000-8000-000000000001",
      "deviceId": "device-sensor-042",
      "seq": 143,
      "type": "reading",
      "timestamp": "2026-10-25T12:06:00.000Z",
      "replayed": true,
      "payload": { "metric": "temperature", "value": 75.1 }
    },
    {
      "eventId": "b1111111-0000-4000-8000-000000000002",
      "deviceId": "device-sensor-042",
      "seq": 144,
      "type": "reading",
      "timestamp": "2026-10-25T12:06:10.000Z",
      "replayed": true,
      "payload": { "metric": "temperature", "value": 76.4 }
    }
  ]
}
```

The batch has a size limit; the simulator sends 50 events per request.

### Per-event results

The request succeeds with `200` as long as the batch itself was understood. Each event gets its own outcome, in the same order as the input, so one bad event does not fail the others:

```json
{
  "status": "batch_processed",
  "summary": { "total": 3, "accepted": 1, "duplicate": 1, "rejected": 1 },
  "results": [
    { "status": "accepted", "eventId": "ev-01" },
    { "status": "duplicate", "eventId": "ev-02", "message": "Duplicate event, already received" },
    { "status": "rejected", "error": "Validation failed", "details": ["payload is required"] }
  ]
}
```

A device should treat `accepted` and `duplicate` as delivered. A `rejected` event is stored on the server for inspection and should not be resent unchanged.

Authentication errors (`401`), rate limits (`429`) and server errors (`5xx`) apply to the whole request. The batch endpoint has its own, larger rate limit than the single-event endpoint, so a reconnect burst is not throttled like normal traffic.

## 5. Idempotency and duplicates

- The server inserts every event into MongoDB first. A unique index on `eventId` makes a second insert of the same id fail, and the API turns that into `status: "duplicate"`. MongoDB decides; a Redis cache is only a fast path and is written after a successful insert, so clearing Redis cannot cause a duplicate to be accepted.
- **"Duplicate" means "already stored", not "already processed".** If a request fails after the event was stored (for example the queue was unavailable and the API replied `503`), the event stays marked `pending` and a recovery sweep queues it later. The device's retry will then receive `duplicate`, and the event is still processed exactly once.
- A duplicate causes no new job, rule evaluation, incident or notification.
- If a queue job is delivered twice, the worker skips an event that is already completed.

---

## 6. Retry and backpressure rules for devices

1. **Never drop an unacknowledged event.** Keep it in a local buffer, on disk if possible, until the server answers `accepted` or `duplicate`.
2. **On `429`:** wait for the `Retry-After` value (use 1 to 2 seconds if the header is missing), add random jitter, then retry.
3. **On `5xx` or a network error:** retry with exponential backoff and jitter, up to a cap. The simulator doubles its delay on each attempt with a cap of about a minute.
4. **Send in order.** Resend buffered events in their original order so that `seq` stays increasing.
5. **After a `rejected` result** (or `400`), do not retry the same content; it will be rejected again.

---

## 7. Offline buffering, replay and the `replayed` flag

When a device cannot reach the platform it keeps generating events and stores them locally. After reconnecting:

1. It sends the buffer in batches with `replayed: true`, oldest first, keeping each event's original `timestamp`.
2. The platform treats an event as a replay if `replayed` is `true` **or** its `timestamp` is more than five minutes older than the time it was received.
3. **Rules still run on replayed events.** A threshold or type rule that matches creates an incident, flagged `fromReplay: true`, so an operator learns what happened during the outage.
4. **Replayed events do not change liveness.** They do not update the device's `lastSeenAt` and do not resolve a stale incident, because old data does not prove the device is healthy now.
5. The first fresh (non-replayed) event updates `lastSeenAt`, marks the device online, and auto-resolves any open stale incident with a timeline entry.

---

## 8. Ordering and clocks

- The server stores the device `timestamp` and `seq` together with its own `receivedAt`. Arrival order is not used to decide the latest reading, and out-of-order events are accepted.
- The platform does not require `seq` to arrive in order and does not reject gaps.
- Liveness (online, stale, offline) uses the **server's receive time**, so a wrong device clock does not cause false stale alerts.
- The five-minute replay rule does use the device clock. A device whose clock runs more than five minutes slow would have its live events treated as replays. Keep device clocks reasonably accurate (for example with NTP); see [LIMITATIONS.md](LIMITATIONS.md).
